# R5: ssh3 × nginx — L4 UDP-прокси, HTTP/3-терминация, ротация сертификата

Дата: 2026-11-11. Стенд: WSL2 loopback (один хост), nginx 1.24.0 (Ubuntu,
`--with-stream=dynamic`, без `http_v3_module`), ssh3-форк @ `4646c60`
(v0.1.41 + R7-T1 ca-bundle; клиент и сервер собраны `go1.22.2` из клона репозитория в WSL).
Топология: `ssh3-server` на `127.0.0.1:8443/udp`, nginx stream UDP-proxy на
`127.0.0.1:4443/udp` → `8443`; кастомный конфиг nginx во временном каталоге стенда,
`/etc/nginx` не затронут. Сертификаты: throwaway CA (EC P-256) + серверные
серты A и B (один CA, SAN `IP:127.0.0.1`, разные ключи и серийники), доверие
клиенту — через `SSH3_CA_BUNDLE` (T1-пул: система ∪ embed ∪ бандл).

**Все цифры — loopback, не транспортные.** Сетевой фактор исключён сознательно
(методика BENCH-2026-09-29 §S1); LAN/WAN-прогоны — отдельная серия. Сравнение
с транспортными цифрами старых бенчей — некорректно.

## Сценарий А: L4 UDP-прокси — работает

`stream { server { listen 127.0.0.1:4443 udp; proxy_pass 127.0.0.1:8443; proxy_timeout 300s; } }`
+ `load_module ngx_stream_module.so` (динамический модуль Ubuntu). Без
терминации TLS: сертификат один, серверный, виден клиенту сквозь прокси.

- Сессии устанавливаются, exec проезжает (одинаковые rc через :8443 и :4443).
- CA-верифицированный хендшейк и пиннинг через прокси работают идентично
  прямому пути (пины `127.0.0.1:4443/ssh3-term` и `127.0.0.1:8443/ssh3-term`
  пишутся независимо, содержат один и тот же серверный серт).
- Стабильность: 5 последовательных + 4 параллельных одноразовых сессий +
  control-master с 3 тёплыми slave-exec — все через nginx, без отказов.

### Замеры (loopback; ssh3 `-insecure` для чистого трафика)

Exec-латентность (cold, 60 итераций, `exec true`, каждая — новый QUIC-коннект):

| Путь | mean, мс | p50 | p90 | min | max |
|------|----------|-----|-----|-----|-----|
| напрямую :8443 | 244.5 | 222.0 | 313.0 | 181.6 | 572.5 |
| через nginx :4443 | 230.9 | 224.0 | 287.5 | 185.1 | 373.9 |

Паритет в пределах шума: p50 отличается на 2 мс; разброс и хвосты сопоставимы.

Throughput (pipe, 128 MiB × 3 прогона, payload в /dev/shm, sha256-верификация
каждого прогона):

| Сценарий | напрямую | через nginx | Отношение |
|----------|----------|-------------|-----------|
| push (`cat \| ssh3 'cat > …'`) | 84.1 MB/s | 55.2 MB/s | ×0.66 |
| pull (`ssh3 'cat …' > файл`) | 107.4 MB/s | 74.3 MB/s | ×0.69 |

Прогонные значения: push 82.6/86.4/83.5 (direct), 64.2/54.2/47.3 (nginx);
pull 106.2/108.2/107.9 (direct), 62.1/80.7/80.1 (nginx).

Чтение: L4 UDP-прокси съедает ~30–35% на loopback. Ожидаемая механика цены:
nginx добавляет userspace-копию датаграмм и его UDP-сессия не наследует
GSO/GRO-оптимизации quic-go (см. B1-IOURING-2026-09-29), а на loopback нет
сетевой компрессии разрыва. На реальной сети доля накладных расходов ниже
(цена делится на сетевой бюджет) — для статьи цифра значит «прокси не
бесплатен, но порядок сохраняет», не «×0.66 навсегда».

### Наблюдения по датаграммам/MTU

- nginx error log (info) за все замеры: только ошибки `sendmsg() failed
  (111: Connection refused)` в окна рестарта сервера (см. ротацию, (б));
  предупреждений о фрагментации/переполнении нет.
- Loopback (MTU 65536) не может surfaced MTU-эффектов: стартовый QUIC-пакет
  1200 B и PMTU-дискавери свободно проходят. Транспортная проверка MTU через
  nginx — отдельный LAN-тест, здесь не покрыт.
- `proxy_responses` не задавался: QUIC-поток двунаправленный, лимит ответных
  датаграмм на сессию не нужен; `proxy_timeout 300s` перекрывает простаивание
  (клиентский keep-alive 1 с держит поток живым).

## Сценарий Б: HTTP/3-терминация на nginx — не взлетает (подтверждено)

Ожидание роадмапа подтвердилось фактически, тремя фактами:

1. **В сборке nginx 1.24.0 (Ubuntu noble) нет `http_v3_module`** — h3-листенер
   невозможен даже на уровне приёма (QUIC-поддержка в nginx появилась в 1.25.1
   mainline; Ubuntu noble пока отдаёт 1.24).
2. **`ssl_certificate` на stream-UDP слушателе парсится, но игнорируется.**
   Проверка: конфиг с `listen … udp; ssl_certificate …` проходит `nginx -t`,
   но с **мёртвым upstream** (прокси в :9999, где никто не слушает) QUIC-хендшейк
   клиента не завершается (timeout, пин не пишется), а в error log виден чистый
   форвард (`sendmsg() failed (111: Connection refused) … bytes from/to
   upstream:0/1200`). Т.е. nginx на UDP — всегда plaintext L4: ни DTLS, ни
   TLS-терминации. (Методическая заметка: первый различающий тест этой гипотезы
   был смешающий — у сервера в тот момент уже стоял серт B после ротации,
   совпавший с сертом nginx-конфига; безупречный вывод даёт именно тест с
   мёртвым upstream.)
3. **Даже при nginx ≥ 1.25.1 схема «клиент→nginx серт A, nginx→ssh3 серт B» не
   собирается:** h3-терминация даёт nginx-свой сертификат и расшифрованный
   HTTP-поток, а upstream-проксирование nginx (`proxy_pass`) говорит по
   HTTP/1.1/h2c **поверх TCP** — HTTP/3-upstream у nginx нет, ssh3-сервер
   слушает только UDP/QUIC, расширенная CONNECT-семантика ssh3
   (`:protocol: ssh3`) проксируется не будет.

**Вердикт:** единственная рабочая топология nginx+ssh3 — L4 UDP-прокси с одним
сквозным серверным сертификатом (сценарий А). Сценарий с двумя сертификатами
(A на фронте, B на бэкенде) для сырого ssh3-over-h3 не реализуем на nginx.

## Ротация сертификата сервера

Серть A (CA-подписан, SAN `IP:127.0.0.1`) → клиент пинится при первом коннекте
(`-strict-host-key-checking accept-new`, доверие через `SSH3_CA_BUNDLE`,
`-insecure` не используется) → смена на серт B (тот же CA, свежий серийник,
новый ключ) + рестарт сервера.

### (а) Новая сессия после ротации — renewal перепин подтверждён

Оба пути (прямой :8443 и сквозь nginx :4443):

```
INF certificate rotated, chain valid: re-pinned 127.0.0.1:8443/ssh3-term in ~/.ssh3/known_hosts
INF certificate rotated, chain valid: re-pinned 127.0.0.1:4443/ssh3-term in ~/.ssh3/known_hosts
```

Пин в known_hosts заменяется на новый серт (по base64-DER пина сверено: серийник
`…ED47B6` → `…ED47B7`), rc=0, последующие коннекты — `Matches` без перепина.
L4-прокси прозрачен для ротации: клиентский renewal срабатывает идентично на
обоих путях, nginx конфигурации не требует.

### (б) Установленная сессия во время рестарта — drain-окно сервера

Ключевой факт: у ssh3-сервера graceful shutdown — SIGTERM прекращает приём
новых соединений, но активные **дрейнят до `SSH3_SHUTDOWN_DRAIN` секунд
(дефолт 5; 0 — закрывать немедленно)**.

Наблюдение (control-master с фоновой сессией `sleep 30`, рестарт с тем же
сёртом A, чтобы отделить рестарт от смены сертификата):

- через ~0.9 с после SIGTERM тёплый exec **сквозь живую QUIC-сессию мастера
  прошёл** (rc=0) — в drain-окне сессия не просто «не закрыта», а функциональна;
- QUIC-соединение мастера умерло после истечения drain (~11 с после SIGTERM по
  наблюдению с опросом 0.5 с; 5 с drain + закрытие + детектирование);
- nginx в этот окно продолжает форвардить клиентские датаграммы в мёртвый
  upstream и честно рапортует в error log (`sendmsg() failed (111: Connection
  refused)`), ответов клиенту не подделывает.

Практика: рестарт ssh3-сервера за nginx L4 при дефолтном drain короткие сессии
(<5 с) переживает; длинные — умирают после drain. Для мгновенного swap-а
сертификата: `SSH3_SHUTDOWN_DRAIN=0` перед стартом нового процесса не поможет —
drain baked в процесс **при старте**, управляется env только у нового экземпляра.
Live reload сертификата у ssh3-сервера нет (сертификат читается на старте) —
ротация = рестарт.

### (в) Resume/0-RTT тикет против нового сертификата

Фактический ответ: **в Go-клиенте cross-run resume не существует**. Тикет-кеш
in-process (`client.GetTicketCache()` в `cmd/ssh3.go`; `client/tickets.go`):
дисковая сериализация невозможна средствами stdlib (`tls.ClientSessionState`
не экспортирует сериализацию) — файл `~/.ssh3/tickets` это артефакт **C-клиента**
(ssh3-c), Go-клиентом не пишется и не читается (sha256 файла до/после прогонов
не изменился; подтверждено прогоном). Каждый CLI-процесс после рестарта сервера
делает полный 1-RTT хендшейк против нового сертификата — и попадает в
renewal-путь (а). Сценарий «старый тикет из кеша против нового серта» в
Go-CLI не воспроизводим by design; для C-клиента это отдельная проверка
(его 0-RTT-кеш лежит в `~/.ssh3/tickets`).

Внутри одного процесса 0-RTT работает (`qconf.Allow0RTT = true`, тикеты через
`NoteDial`), но жизненный цикл CLI-сессии через рестарт сервера не живёт —
проверка «тикет старого процесса против нового серта» не имеет в Go-клиенте
носителя.

## Итоги для статьи R1

1. nginx+ssh3 — только L4 UDP-прокси, один сквозной сертификат; «двухсертифи-
   катная» схема на nginx не реализуема (нет h3-upstream, UDP-слушатель не
   терминирует TLS).
2. Цена L4-прокси на loopback ≈ 30–35% throughput, exec-latency — паритет;
   на реальной сети доля ниже (loopback-цифры не транспортные).
3. Ротация: рестарт с drain (дефолт 5 с, короткие сессии переживают), клиенты
   с CA-верифицированным renewal перепинываются автоматически на обоих путях
   (прямой и через прокси); Go-клиент cross-run resume не имеет — «старый тикет
   против нового серта» не существует.
